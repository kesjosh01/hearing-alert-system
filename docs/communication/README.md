# S3–C3 이벤트 프로토콜 v1 및 양 팀 구현 규칙

작성일: 2026-11-07. 공유 대상: S3 제어·ML 팀, C3 디스플레이·진동 팀.

## 0. 이 문서로 Codex에 구현을 맡길 때의 작업 규칙

### 읽는 방법과 우선 확인

이 파일은 단독으로 전달할 수 있는 통신 규격 및 구현 지시서다. 모든 파일 경로는 **문서가 저장된 폴더가 아니라 Git 저장소 루트 기준**의 일반 텍스트다. Markdown 상대 링크나 특정 PC의 절대 경로에 의존하지 않는다. 바탕화면에 둔 문서의 위치를 기준으로 소스 경로를 조합하지 않는다.

1. 전달받은 저장소의 루트와 현재 브랜치·커밋·작업 변경사항을 확인한다. 해당 작업에 적용되는 `AGENTS.md`와 기존 코드를 다시 읽는다. 아래의 “파일 없음/구현 전” 기록은 작성 당시 상태이므로 현재 상태와 다르면 현황을 보고한다.
2. 팀이 같은 저장소를 사용하더라도 브랜치·커밋 차이가 있을 수 있다. 같은 코드라고 가정하지 않는다. 코드 갱신이 필요하면 로컬 변경을 보존하고 프로젝트의 Git 작업 규칙에 따라 진행한다. 이 문서 자체는 자동 pull·커밋·push·플래시 지시가 아니다.
3. 요청에 담당 팀이 지정돼 있으면 해당 팀 범위를 구현한다. 지정되지 않으면 S3·ML과 C3 양쪽의 아래 범위를 전체 목표로 삼는다. 이미 동작하는 구현은 확인 후 재사용한다.
4. 확정된 통신 규칙(3~6절)은 준수한다. 문서와 현재 코드가 다르면 규격 변경을 임의로 하지 말고 차이를 보고하고 구현 수정 범위를 판단한다. 새 합의가 필요한 부분만 확인하며 독립적으로 가능한 작업은 계속한다.

### 구현해야 할 기능

**ML·LED·디스플레이·진동은 구현 범위에 포함한다.** 통신 인코더·디코더나 TEST 로그만 만들고 전체 작업 완료로 보고하지 않는다.

| 담당 | 필수 구현 범위 | 연결 지점 |
| --- | --- | --- |
| S3·ML 팀 | 오디오 입력·전처리·모델 추론, FIRE_ALARM/DOORBELL 분류 결과 생성, 모델 라벨과 고정 이벤트 ID 매핑, 두 이벤트 동시 감지 처리 | 추론 결과 → S3 제어 코드 → 정규 ID 목록 |
| S3 제어 팀 | 두 ID에 따른 자체 LED 제어, 별개 이벤트 보관·순번 부여·UDP 송신·ACK 검증·재전송 | 같은 정규 ID를 LED와 송신 양쪽에 전달 |
| C3 팀 | UDP 검증·중복 처리·접수 큐, 두 ID에 대응하는 디스플레이 표시와 진동 제어, 접수 성공 후 ACK | 검증된 이벤트 → 알림 작업 → 실제 출력 드라이버 |
| 양 팀 공통 | 공용 프로토콜 정의·인코딩·검증, 정상/오류 벡터 자동 검증, 빌드 및 통합 시험 절차 | 저장소 내 공유 가능한 모듈 재사용 |

모델·마이크·GPIO·디스플레이 종류/버스·모터 구동 회로·이벤트별 LED/표시/진동 패턴은 이 프로토콜만으로 확정하지 않는다. 기존 코드·회로·팀 문서에 합의된 값이 있으면 재사용하고 근거를 적는다. 없으면 필요한 모델 파일·라벨 목록·전처리 조건·장치 사양·핀 배치 및 알림 표현을 확인한다. 동시 감지는 어느 한 종류만 남기는 단일 argmax 경로만으로 충족했다고 보지 않는다.

모델 선정·학습·평가·변환이 필요한데 준비된 산출물이 없으면 해당 작업을 ML 범위의 남은 작업으로 명시한다. 가짜 추론값이나 로그 출력·목 드라이버는 로컬 검증에만 사용하고 실제 ML·하드웨어 기능 구현 완료로 보고하지 않는다. 실제 장치 구성이 확인되기 전 임의 GPIO에 출력하는 코드를 기본 활성화하지 않는다.

### 미결정 사항과 변경 경계

- 큐 총 크기·넘침·유효시간·장기 단절·재시도 종료·영구 보관·알림 우선순위/선점은 미결정이다. 임의로 제품 정책을 확정하지 않는다. 동시 두 이벤트 보관·별도 전달이라는 확정 요구는 지킨다. 정책과 무관한 인터페이스·파서·기본 연동은 먼저 구현하고 정책에 종속된 부분만 구분해 보고한다.
- **C3 절전 방식과 1회 300 ms 수면 적용은 토의 후 결정한다.** 이 작업에서 자동 Light-sleep을 확정 설계로 선언하거나 수면 시간·수신 타임아웃·비콘/DTIM·Wi-Fi 절전 설정을 변경하지 않는다. 기존 `ACK_TIMEOUT_MS=300`은 S3 재전송 설정이며 C3 수면 시간으로 재해석하지 않는다. 수신/알림 구현에 절전 변경이 꼭 필요하면 이유와 대안을 먼저 제시한다.
- 미등록 ID를 임의 추가하거나 기존 ID·필드·ACK 의미를 변경하지 않는다. 7절의 기존 구현 설명을 미결정 제품 정책의 승인으로 해석하지 않는다.
- 근거 경로가 없으면 파일명을 비슷하게 추정해 구현하지 않는다. 저장소에서 관련 구현을 찾고, 찾지 못한 기능과 필요한 입력만 구체적으로 보고한다.

### 구현 완료 기준과 결과 보고

1. 담당 범위의 실제 기능을 연결한다. S3는 분류 → 고정 ID → LED·송신, C3는 검증 → 접수 → 디스플레이·진동까지 이어져야 한다. 미결정 입력으로 막힌 부분은 완료와 구분한다.
2. 6절의 정상 EVENT/ACK 4개와 오류 벡터를 실제 구현한 공용 코드에 적용해 자동 검증한다. 매핑, 동시 두 이벤트 보관/전송, 중복 억제, ACK 필드 불일치 및 접수 실패 경로도 검증한다. 모델 정확도는 통신 벡터 검증과 별도로 평가한다.
3. 변경한 담당 타깃을 실제 빌드한다. 공용 코드에 영향을 주면 S3와 C3 양쪽을 빌드한다. 저장소의 현재 빌드 설정을 사용하고 빌드 성공을 실기기 동작 성공으로 표현하지 않는다.
4. 보드 연결이 없으면 가능한 로컬 검증을 수행하고 8절의 실기기 시험을 미수행으로 남긴다. 물리 LED·표시·진동과 절전 중 전달은 실기기 시험 전 완료 검증으로 보고하지 않는다.
5. 최종 보고에는 변경 파일, 구현한 기능, 적용한 규격, 빌드/자동 검증 결과, 미결정 사항·필요 입력, 남은 실기기 시험을 적는다. 담당 범위의 기능 일부만 구현했으면 부분 완료라고 명시한다.

## 1. 적용 범위와 확인 상태

이 문서는 기존 SoftAP UDP 기초 실험 명세를 갱신한 **소리 이벤트 통합용 설계 계약**이다. 기존 16바이트 v1 프레임을 유지하고 이벤트 ID와 처리 경계를 정의한다. 소리 이벤트·LED·디스플레이·진동 연동은 아직 구현하지 않았다. 명세 작성 시점에는 두 보드가 연결되어 있지 않았다. 이는 작성 당시 검증 조건이며, 이 문서를 받은 팀의 코드 구현 범위를 제한하는 문장이 아니다. 현재 문서 갱신 작업은 명세 보완이며, 아래 구현은 각 팀의 후속 작업이다.

SoftAP 연결 이력만으로 전송 방식을 추정하지 않았다. 아래 코드에서 UDP와 직렬화 형식을 직접 확인했다. 과거 실물 결과와 현재 코드 확인, 이번 규격에서 도출한 예시는 별개다.

| 확인 대상 | 근거 파일·위치 | 확인 내용 |
| --- | --- | --- |
| 저장소 지침 | 저장소 및 상위 경로의 `AGENTS.md` 검색 | 적용할 파일 없음 |
| 프로젝트 현황 | 루트 README (`README.md`), 구조 문서 (`docs/architecture/README.md`) | TEST 통신 실험과 최종 통합의 구분 |

기존 ESP-NOW 영역 (`communication_tests/espnow/README.md`)은 참고 안내뿐이며 구현이 없다. 현 소스의 무선 설정은 2.4GHz, 채널 6, WPA2-PSK, 수신부 1대, AP 주소 `192.168.4.1`이다. 전송 매체는 이 코드에 근거해 UDP를 채택한다. 외부 자료 조사는 수행하지 않았다.

## 2. 두 팀의 데이터 흐름과 구현 경계

```text
S3: ML 추론 결과(모델 클래스 번호·라벨 집합)
    → S3 제어 코드의 명시적 매핑 → 정규 이벤트 ID 목록
    ├→ S3 자체 LED 처리기(각 ID 전달)
    └→ 이벤트 송신 대기열 → v1 인코더 → UDP → C3
C3: 송신원·프레임·이벤트 검증 → 중복 검사
    → 디스플레이·진동 알림 처리기 접수 → ACK
```

- **S3 팀:** 모델별 클래스 번호/라벨 → 아래 고정 ID의 매핑 테이블을 제어 코드에서 관리한다. 예를 들어 모델의 클래스 번호가 바뀌어도 통신 ID는 바뀌지 않는다. 클래스 인덱스를 그대로 전송하지 않는다. 미매핑 결과·배경음은 전송하지 않고 필요시 진단한다. 감지 임계값·시간 창·반복 감지 억제는 별도 ML/제어 정책이다.
- S3 LED와 전송에는 같은 정규 ID를 사용한다. LED 처리는 C3 ACK를 기다리지 않는다. LED 패턴·동시 알림 표현은 별도 제어 정책이다.
- **C3 팀:** 모델 클래스 정보를 해석하지 않는다. 검증된 ID를 `handle_event(event_id, session, seq)`와 같은 논리 인터페이스로 디스플레이·진동 처리기에 넘긴다(함수명은 제안이며 구현 없음). 알림 재생 완료를 기다리지 않고 접수 성공 뒤 ACK한다. 처리기/큐가 접수하지 못하면 중복 기록을 갱신하거나 ACK하지 않는다.
- 공통 구현 지점은 현재 `main.c`의 `send_packet()`/수신 검사다. S3의 주기적 TEST 생성·상수 `1` 송신을 매핑·대기열 기반 생성으로 교체하고, ACK 검사는 현재 대기 중인 `(session, seq, event_id)` 전체와 비교한다. C3의 `value == 1` 검사·TEST 로그를 등록 ID 검사·처리기 접수로 교체한다. 최종 펌웨어는 `firmware/transmitter_s3/`와 `firmware/receiver_c3/`에 통합하고 공통 인코더·검증기를 공유한다.

## 3. 고정 이벤트 ID와 확장 규칙

이벤트 ID는 unsigned 32비트 정수다. 메시지 종류 `EVENT=2`와 이벤트 ID는 다른 필드다.

| ID (hex / decimal) | 이름 | 의미 | 사용 |
| --- | --- | --- | --- |
| `0x00000000` / 0 | 예약 | 이벤트 아님 | EVENT에서 거부 |
| `0x00000001` / 1 | TEST | 기존 통신 실험 | 실험 전용 예약, 소리 이벤트로 재사용 금지 |
| `0x00000100` / 256 | FIRE_ALARM | 화재경보 소리 감지 | v1 소리 이벤트 |
| `0x00000101` / 257 | DOORBELL | 초인종 소리 감지 | v1 소리 이벤트 |

v1 소리 수신기는 FIRE_ALARM·DOORBELL 두 ID만 처리한다. TEST 호환이 필요하면 별도 실험 모드를 명시적으로 사용한다. TEST를 화재 알림으로 해석해서는 안 된다. 나머지는 미등록 ID로 폐기하고 알림·성공 ACK·중복 기록 갱신을 하지 않는다. 진단 로그는 허용한다.

향후 ID는 이 표에 중복 없이 추가하고 양 팀의 매핑·수신 허용 목록·벡터를 함께 갱신한다. 할당한 ID는 의미를 바꾸거나 삭제 후 재사용하지 않는다. 신규 소리 ID는 `0x00000102`부터 미할당 값을 순차 배정한다. ID만 추가하고 프레임 의미가 같으면 v1을 유지할 수 있으나 구형 수신기는 이를 거부하므로 호환성을 확인한 뒤 배포한다. 필드 순서·크기·인코딩 또는 기존 필드 의미를 바꾸면 새 프로토콜 버전을 사용한다. 기능 협상은 현재 없다.

## 4. 전송 형식과 수신 검사

**UDP 데이터그램 1개 = 프레임 1개 = 소리 이벤트 1개**다. 정확히 16바이트의 바이너리이며 JSON·CSV·UTF-8 이벤트 이름·ASCII hex 문자열을 보내지 않는다. 아래 hex는 바이트 표시법이다. 별도 줄바꿈·NUL·길이 필드·타임스탬프·confidence·비트마스크는 없다.

| 오프셋 | 바이트 수 | 필드 | 인코딩 / EVENT의 값 |
| --- | --- | --- | --- |
| 0 | 2 | magic | ASCII `HA` = `48 41` |
| 2 | 1 | version | unsigned 8비트, `01` |
| 3 | 1 | type | unsigned 8비트, EVENT=`02` |
| 4 | 4 | session | unsigned 32비트 big-endian, S3 부팅 세션 |
| 8 | 4 | seq | unsigned 32비트 big-endian, 1부터 증가 |
| 12 | 4 | event_id / value | unsigned 32비트 big-endian, 위 ID |

세션은 기존 코드처럼 S3의 `esp_random()` 32비트 값이며 0도 유효하다. 난수 충돌 가능성이 있다. seq=0은 EVENT에서 무효다. 순번 소진 시 새 세션을 만들고 seq=1부터 시작한다. 같은 이벤트 재전송은 세션·순번·ID를 그대로 유지한다. 신규 이벤트는 새 순번을 사용한다.

기존 제어·진단 패킷도 같은 헤더·길이·바이트 순서를 유지한다.

| type | 방향 | session | seq | value |
| --- | --- | --- | --- | --- |
| HELLO=1 | C3 → S3 | C3 부팅 세션 | 0 | 0 |
| EVENT=2 | S3 → C3 | S3 부팅 세션 | 이벤트 순번 | 이벤트 ID |
| ACK=3 | C3 → S3 | 받은 EVENT 값 복사 | 받은 EVENT 값 복사 | 받은 EVENT 값 복사 |
| PM_STATS=4 | C3 → S3 | C3 부팅 세션 | SDK Light-sleep 성공 횟수 | 거절 횟수 |
| POWER_STATE=5 | C3 → S3 | C3 부팅 세션 | auto Light-sleep 설정 0/1 | Wi-Fi MIN_MODEM=1 |

수신 검사는 다음 순서로 한다.

1. 실제 수신 데이터그램 길이가 정확히 16인지 확인한다. 짧거나 긴 메시지는 폐기한다. 16바이트 버퍼로 긴 데이터그램을 잘라 정상으로 인정하면 안 된다. 기존 코드는 17바이트 수신 버퍼로 초과를 검출한다.
2. magic=`48 41`, version=1인지 확인한다. 알 수 없는 버전은 v1로 추측해 파싱하지 않는다.
3. type·방향·송신 IP·포트를 검사한다. C3 EVENT는 AP IP에서 포트 4210으로 온 것만, S3 ACK는 등록 C3 IP·포트에서 온 것만 처리한다. 진단 패킷은 등록된 C3 세션도 확인한다. 미등록 종류는 폐기한다.
4. 필드를 명시적으로 big-endian 디코딩한다. EVENT는 seq≠0, 등록된 소리 ID인지 확인한다. ACK는 대기 이벤트의 세 필드가 모두 일치해야 대기를 해제한다. HELLO·상태 패킷은 위 표의 필드 조건을 적용한다.
5. 유효 이벤트만 중복 검사 후 처리기에 접수한다. 동일 세션에서 이미 접수한 순번 이하이면 알림을 반복하지 않고 ACK만 다시 보낸다. 새 이벤트는 접수 성공 뒤 기록·ACK한다. 잘못된 프레임은 처리기 호출·ACK·중복 상태 변경 없이 폐기한다.

ACK는 **소프트웨어 접수 확인**이며 디스플레이 표시·모터 동작 완료·사용자 인지의 증명이 아니다. 현재 코드는 TEST 로그 후 ACK할 뿐 처리기 접수 실패 경로가 없다. 애플리케이션 인증도 없어 IP·포트 검사는 발신자 인증을 보장하지 않는다.

## 5. 동시 감지

한 추론 구간에서 두 소리가 검출되면 S3 매핑 결과는 두 ID의 목록이다. 한 개로 덮어쓰거나 두 ID를 OR하지 않는다. 동일 배치의 생성 순서는 FIRE_ALARM, DOORBELL로 정하고 각각 고유 순번을 부여한다. 이는 큐 입력 순서이며 알림 우선순위·선점 정책을 확정하지 않는다.

기존 순번 기반 중복 판정과 맞도록 S3는 **stop-and-wait**로 전송한다. 첫 이벤트 ACK 후 두 번째를 전송한다. 이를 위해 활성 전송 1개 외에 같은 배치의 두 번째 이벤트도 보관할 대기열이 필요하다. 현재 단일 TEST 보관 코드로는 이 흐름이 구현되지 않는다. C3는 첫 이벤트 알림이 진행 중이어도 두 번째 이벤트를 독립적으로 접수할 수 있어야 한다. 표시·진동의 순차 실행/선점은 처리기 정책으로 별도 결정한다.

최소한 두 이벤트를 보관해야 하지만 장기 단절 시 필요한 총 큐 크기·넘침·만료 정책은 7절의 후속 결정 사항이다. 이 설계는 동시 감지 두 개를 표현할 수 있다는 계약이며 모든 장애 상황에서 전달을 보장하는 계약이 아니다. 병렬 송신으로 바꾸면 역순 수신을 누락시키는 현 중복 판정을 재설계해야 한다.

## 6. 규격에서 도출한 테스트 벡터

아래는 **규격에서 도출한 예시**이며 실기기 송수신 캡처가 아니다. session=`0x12345678`(305419896), 올바른 송신원, 초기 중복 기록 없음, 처리기 접수 성공을 가정한다. 각 줄은 정확히 16바이트의 UDP payload이며 공백·개행 문자는 전송하지 않는다.

| 벡터 | 정확한 전송 데이터 (hex) | 기대 디코딩 |
| --- | --- | --- |
| FIRE_ALARM EVENT | `48 41 01 02 12 34 56 78 00 00 00 01 00 00 01 00` | version=1, type=2, session=305419896, seq=1, event_id=256 (FIRE_ALARM) |
| FIRE_ALARM ACK | `48 41 01 03 12 34 56 78 00 00 00 01 00 00 01 00` | type=3, EVENT의 session·seq·ID 일치 |
| DOORBELL EVENT | `48 41 01 02 12 34 56 78 00 00 00 02 00 00 01 01` | version=1, type=2, session=305419896, seq=2, event_id=257 (DOORBELL) |
| DOORBELL ACK | `48 41 01 03 12 34 56 78 00 00 00 02 00 00 01 01` | type=3, EVENT의 session·seq·ID 일치 |

각 EVENT는 S3 LED 처리기에 해당 ID를 전달하고 C3에서는 해당 ID의 디스플레이·진동 처리기에 한 번 접수된다. 위 두 EVENT를 같은 감지 배치에서 생성한 경우 첫 ACK 후 둘째를 보내며 두 처리기 접수가 모두 확인되어야 한다. 현재 예제는 이 ID들을 거부하므로 양 보드의 소리 ID 지원을 함께 구현한 뒤 시험한다.

잘못된 메시지 예시는 FIRE_ALARM EVENT를 기준으로 아래처럼 바꾼다. 변경 후 전체 바이트열이 시험 입력이며 오프셋은 0부터다.

| 입력 / 조건 | 기대 동작 |
| --- | --- |
| 마지막 바이트 삭제 (15바이트), 또는 끝에 `00` 추가 (17바이트) | 길이 오류, 폐기·ACK 없음 |
| 오프셋 0을 `00`으로 변경 | magic 오류, 폐기·ACK 없음 |
| 오프셋 2를 `02`로 변경 | 미지원 버전, 폐기·ACK 없음 |
| 오프셋 3을 `FF`로 변경 | 미등록 종류, 폐기·ACK 없음 |
| 오프셋 8~11을 `00 00 00 00`으로 변경 | seq=0, 폐기·ACK 없음 |
| 오프셋 12~15를 `00 00 01 02`로 변경 | 미등록 ID=258, 폐기·알림·ACK 없음 |
| 오프셋 12~15를 `00 00 00 00` 또는 `00 00 00 01`로 변경 | 예약 또는 TEST ID, 소리 수신 모드에서 거부 |
| 정상 FIRE_ALARM을 같은 세션·순번으로 재수신 | 첫 접수 1회만, 동일 ACK 재전송 |
| seq=2 접수 후 같은 세션의 seq=1 도착 | 기존 stop-and-wait 정책상 stale, 알림 없이 ACK. 병렬 송신 금지 이유 |
| 정상 payload지만 잘못된 IP·포트 또는 방향 | 폐기·ACK 없음 |
| S3가 기다리는 ACK와 session·seq·ID 중 하나라도 다름 | ACK 무시, 해당 이벤트 대기 유지 |
| 처리기 큐 접수 실패 | 알림 접수·중복 기록·성공 ACK 없음. 재시도 시 다시 접수 가능해야 함 |

## 7. 절전·보관·ACK: 확인된 구현과 추가 결정

| 항목 | 기존 코드에서 확인된 동작 | 소리 이벤트 통합 시 추가 결정/작업 |
| --- | --- | --- |
| C3 절전 | MIN_MODEM + 부팅 유예 후 자동 Light-sleep. S3 AP는 유지. Deep-sleep 아님 | 실제 디스플레이·진동 부하에서 절전·수신 지연 재시험. AP/드라이버 버퍼 크기·보존시간은 코드에서 보장하지 않음 |
| S3 이벤트 보관 | RAM의 TEST 1개, ACK까지 다음 TEST 생성 지연. heartbeat 만료·HELLO 재등록에도 보관 | 실제 두 ID의 대기열 구현, 최대 크기·넘침·우선순위·유효시간·미접속 중 감지 처리 결정 |
| 재전송 | 최초 포함 4회 묶음, 미확인 시 RAM 유지 후 2초 간격으로 다음 묶음. 같은 세션·순번 사용 | 소리 ID 저장·재전송, 재시도 중 신규 감지 보관. 재시도 종료/취소·장기 단절 정책 결정 |
| ACK | TEST 수신 로그/중복 판정 뒤 원래 세 필드 복사. S3는 현재 값 1만 확인 | 처리기 접수 성공의 ACK로 연결하고 대기 이벤트 ID 비교로 변경. 접수 실패를 위한 별도 NACK는 v1에 없음 |
| 중복 | C3 RAM의 마지막 S3 세션·최대 순번. 같은 세션의 이하 순번은 재실행 없이 ACK | 소리 처리기 접수 성공 시에만 기록. 재부팅·세션 교대·지연 패킷을 포함한 보존/세션 합의 필요 여부 결정 |
| 재부팅·단절 | S3 재부팅 시 보관 이벤트 유실, C3 재부팅 시 중복 기록 유실. C3 재접속 및 IP 획득 후 HELLO 전송 구현 | 영구 저장 여부·전원 복구·세션 충돌 정책 결정. exactly-once, at-least-once 또는 기한 내 전달 보장을 주장할 수 없음 |

**C3의 1회 300 ms 수면은 토의 후 결정할 별도 펌웨어 설정 후보**로만 기록하며, 이 문서에 따른 구현에서 적용하지 않는다. 현 소스에 `ACK_TIMEOUT_MS=300`이 존재한다는 것은 코드 현황이며, v1 메시지 필드·프레임 형식·수신 유효 조건·전달 보장 시간/조건에 포함하지 않는다. 절전 주기나 반드시 지켜야 하는 전달 지연으로 해석하지 않는다. 적정값은 추후 절전·알림 부하·ACK 유실 시험으로 결정한다. 위 재시도 횟수·묶음 간격 역시 기존 구현 설명이며 소리 이벤트의 전달 보장 조건이 아니다.

기존 재접속·보관 변경은 아직 실물 검증되지 않았고, 2026-10-30 결과 (`docs/test_results/low_power_2026-10-30.md`)는 변경 전 TEST 펌웨어의 측정이다. 이를 소리 이벤트·절전 중 무손실 전달의 증거로 쓰지 않는다.

## 8. 검증과 후속 통합 시험

### 명세 최초 작성 때 수행한 로컬 검증 (보드 연결 없음)

- 저장소 지침·README·기존 통신/절전 문서 및 공통 S3/C3 송수신 소스를 검토했다. 최종 펌웨어 경로에 별도 구현이 없음을 확인했다.
- 문서의 네 정상 hex 벡터를 독립적인 Python big-endian 직렬화/역직렬화로 비교하고, 길이·magic·버전·종류·순번·등록 ID 오류 벡터를 참조 검사했다.
- 소스의 실제 `put32()`/`get32()`를 추출한 호스트 C 하네스에서 두 EVENT payload가 문서 벡터와 일치하는지 확인했다. 이는 정수 인코딩 검증이며 실제 소리 ID 수신 지원을 검증한 것이 아니다.
- 최초 작성본의 상대 링크와 `git diff --check`를 검사했다. 단독 전달용 갱신본에서는 상대 링크를 저장소 루트 기준 경로 표기로 대체했다. 펌웨어 변경·빌드·플래시·무선 송신·실물 알림 시험은 수행하지 않았다.

위 로컬 검증은 명세 예시의 일관성과 기존 인코딩과의 일치를 확인한다. 펌웨어에 새 ID·큐·처리기 연동이 구현됐다는 의미는 아니다. 이후 실제 공통 파서·큐가 구현되면 동일 벡터로 파서 거부·ACK 일치·접수 실패·중복 억제를 자동 시험한다.

### 두 보드 연결 후 수행할 통합 시험 (미수행)

1. 양 보드에 새 ID·대기열·처리기 접수를 구현하고 빌드한다. DHCP → HELLO → EVENT → ACK와 세 필드 일치를 확인한다.
2. ML 매핑 입력별로 FIRE_ALARM/DOORBELL ID가 생성되고 S3 LED 및 C3 디스플레이·진동이 각각 동작하는지 확인한다. 모델 클래스 재정렬에도 통신 ID가 유지돼야 한다.
3. 동일 추론 구간에 두 소리를 넣어 각각의 순번·대기열·ACK·처리기 접수 및 실제 두 알림을 확인한다. 첫 ACK 지연 중에도 둘째가 덮어써지지 않아야 한다.
4. 실제 C3 절전 성공 카운터 증가를 확인한 상태에서 감지·연속 전송·왕복 지연·소비전류를 측정한다. 절전 설정 활성화만으로 실제 절전 성공을 판정하지 않는다.
5. ACK 유실·중복·역순·미등록 ID·잘못된 버전/길이/IP/포트·처리기 큐 포화를 주입해 4~6절 동작을 확인한다. 수신 거부 시 중복 상태가 바뀌지 않아야 한다.
6. 장기 단절·재접속·S3/C3 각각의 재부팅·세션 변경 및 큐 넘침/만료를 확정 정책에 맞춰 시험한다. RAM 유실·중복 재처리 가능성도 기록한다.

시험 조건, 펌웨어 리비전, 원본 양측 로그, 고유 감지/접수/ACK 수와 실제 알림 결과를 시험 기록 영역 (`docs/test_results/README.md`)에 남긴다. ACK 수만으로 물리 알림 성공을 판정하지 않는다.
